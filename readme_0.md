# Спецификация проекта study (AI Advent Challenge)

Учебный проект в рамках AI Advent Challenge: локальное веб-приложение для экспериментов
с большими языковыми моделями (LLM) через OpenAI-совместимые API. Приложение объединяет
три режима работы — интерактивный чат с настройками генерации, пакетное сравнение
настроек и автономный агент с инструментами.

- **GroupId / ArtifactId:** `ru.tionstudio.ai.advent.challenge:study:1.0-SNAPSHOT`
- **Язык интерфейса:** русский
- **Кодовая база:** ~8 900 строк (13 классов Java + 3 веб-страницы)

---

## 3. Конфигурация (`config.properties`)

Файл не коммитится (содержит API-ключи); шаблон — `config.properties.example`.

### Группы моделей

```properties
llm.models=cloud,local,gemini                  # список id групп через запятую

llm.models.<id>.model=openai/gpt-4o-mini       # имя модели для API
llm.models.<id>.api.key=sk-...                 # ключ (для локальных — любой placeholder)
llm.models.<id>.api.base-url=https://...       # OpenAI-совместимый base URL
llm.models.<id>.price.prompt=0.15              # опц.: цена $ за 1M prompt-токенов
llm.models.<id>.price.completion=0.60          # опц.: цена $ за 1M completion-токенов
llm.models.<id>.context-window=4096            # опц.: размер контекстного окна (токены)
```

### Прочие ключи

| Ключ | Назначение | По умолчанию |
|---|---|---|
| `llm.default-model` | id группы по умолчанию | первая группа |
| `llm.analysis.model` | id группы для анализа результатов пакетного режима | default |
| `server.port` | порт веб-сервера | 8080 |
| `log.file` | путь к кольцевому логу | `app.log` |
| `log.max-records` | число последних записей в логе | 100 |

Поиск группы выполняется по id или по имени модели (без учёта регистра). Если группы не
заданы, поддерживается legacy-схема одиночного провайдера (`llm.provider`, `llm.api.*`,
`llm.local.*`).

## 4. Архитектура

### 4.1. Сборка приложения (`Main`)

1. Загружает `AppConfig`, настраивает `RingFileLogHandler`.
2. Создаёт по одному `LlmClient` на каждую группу моделей.
3. Открывает `settings.db` и инициализирует три хранилища: `PresetStore`,
   `ConversationStore`, `AgentDialogStore`.
4. Создаёт `AgentTools` с песочницей в каталоге `test/`.
5. Запускает `ChatServer` на порту из конфигурации.

### 4.2. Клиент LLM (`LlmClient`)

- Потоковые запросы (`"stream": true`, `stream_options.include_usage: true`): токены
  ответа передаются потребителю по мере поступления, отдельно стримятся токены
  «мышления» reasoning-моделей (поля `reasoning` / `reasoning_content`).
- Повторные попытки при HTTP 429/500/502/503/504 — до 4 попыток с backoff 2/5/10 с.
- Параметры запроса (`ChatOptions`): формат ответа, max_tokens, stop-последовательности,
  `reasoning_effort` (low/high/max), температура (0..2).
- Форматы ответа реализованы через системный промпт: `none`, `json`, `xml`, `yaml`,
  `markdown-table`, `chain-of-thought`, `styled` (произвольный стиль; по умолчанию —
  «системный аналитик»).
- Результат (`ChatResult`): текст, usage-токены (prompt/completion/total/reasoning),
  `finish_reason`, полный текст скрытых рассуждений.
- `chatOnce()` — нестриминговый вызов для вспомогательных задач (суммаризация).

### 4.3. Пост-обработка ответов (`ResponseParser`)

Извлечение данных из ответа модели запросом на выбор: **JSONPath** (Jayway) по ответу
как JSON или **XPath** по ответу как XML (с XXE-защитой: DTD и внешние сущности запрещены).
Ошибки парсинга возвращаются в чат, а не рушат запрос.

### 4.4. Контекст диалога (`ConversationManager` + `ConversationStore`)

Режим «Сохранять контекст» в чате:

- история хранится на сервере в SQLite (id диалога — UUID);
- лимит контекста: в сообщениях или в токенах (оценка ~3 символа/токен для русского);
- стратегии сжатия переполнения: `truncate` (обрезка), `summarize` (LLM-сводка старых
  сообщений, добавляется системным сообщением), `hybrid` (сводка + гарантированно
  последние 6 сообщений дословно);
- сжатие best-effort: при сбое суммаризации — тихий откат к обрезке;
- в UI передаются метрики: заполнение лимита (%), число удержанных сообщений, токены,
  потраченные на суммаризацию.

### 4.5. Логирование (`RingFileLogHandler`)

Файловый лог-«кольцо»: файл всегда содержит только последние N записей (по умолчанию 100)
и перезаписывается на каждую запись. Формат — одна строка: дата, время, логгер, уровень,
сообщение. Ошибки записи лога игнорируются (лог не должен ломать приложение).

## 5. HTTP API

Сервер — `com.sun.net.httpserver`, пул потоков — виртуальные потоки
(`newVirtualThreadPerTaskExecutor`). Страницы обновляются по SSE (Server-Sent Events);
пока модель молчит, каждые 10 секунд отправляется keep-alive-комментарий, чтобы
промежуточные прокси не рвали соединение.

| Эндпоинт | Метод | Назначение |
|---|---|---|
| `/api/chat` | POST | один ход чата (SSE-стрим токенов) |
| `/api/agent/chat` | POST | один ход агента (SSE-стрим событий) |
| `/api/agent/permission` | POST | разрешение/запрет файловой операции агента |
| `/api/agent/control` | POST | `pause` / `resume` / `abort` / `compress` для сессии агента |
| `/api/agent/session?id=` | DELETE | сброс сессии агента («Новый диалог») |
| `/api/agent/history` | GET | восстановление текущего диалога агента после перезапуска |
| `/api/presets` | GET / POST / DELETE | список, сохранение (upsert по имени), удаление пресетов |
| `/api/conversations?id=` | GET / DELETE | загрузка / удаление диалога чата |
| `/api/models` | GET | группы моделей, модель по умолчанию и модель анализа |
| `/*` | GET | статика из `web/` (с защитой от path traversal) |

### 5.1. `POST /api/chat`

Тело: `{"message": "...", "model"?, "useCloud"?, "format"?, "formatDescription"?, "maxTokens"?, "stopSequences"?, "reasoningEffort"?, "temperature"?, "useContext"?, "contextLimit"?, "conversationId"?, "parseMode"?, "parseExpression"?}`.

Выбор клиента: `useCloud=true` → модель анализа; поле `model` (id или имя) → выбранная
группа; иначе — модель по умолчанию.

SSE-события: `conversation` (id диалога), `context` (метрики сжатия), `token`,
`reasoning`, `done` (полный ответ + применённые настройки + статистика токенов/времени +
результат парсинга), `error`.

### 5.2. `POST /api/agent/chat`

Тело: `{"message": "...", "sessionId"?, "compression"?: "none"|"lastN"|"summary"|"sliding"|"sticky", "contextMessages"?, "slidingMessages"?, "stickyKeep"?, "factsMax"?, "factsConsolidate"?, "maxToolCalls"?, "planning"?, "summaryKeep"?, "summaryEvery"?, "tools"?}`.

SSE-события: `session`, `planning`, `plan`, `token`, `reasoning`, `reply`, `reply_error`,
`tool_call`, `tool_result`, `permission_request`, `permission_resolved`, `limit_confirm`,
`limit`, `paused`, `resumed`, `note`, `summary`, `facts`, `done`, `error`.

### 5.3. Checkpoints агента

- `POST /api/agent/checkpoint` — сохранить checkpoint диалога:
  `{"dialogId", "label", "settings"?, "turn"?}` → `{"id", "label", "entryId"}`. Снимок
  хранит id последней записи диалога (граница форка) и JSON мутируемого состояния вне
  записей: список фактов (sticky) и настройки панели. Необязательный `turn` (1-based,
  ходы считаются по записям `user`) фиксирует снимок на конце указанной пары
  вопрос-ответ: граница — последняя запись перед началом следующего хода; факты берутся
  из последней журнальной записи `facts` в пределах границы (для диалогов без журнала —
  из живой таблицы), summary — из последней записи `summary` ≤ границы (она копируется
  вместе с записями при форке).
- `GET /api/agent/checkpoint?dialog=<id>` — список checkpoint'ов диалога.
- `DELETE /api/agent/checkpoint?id=<N>` — удалить checkpoint (диалог не трогается).
- `POST /api/agent/checkpoint/fork` — материализовать checkpoint в НОВЫЙ независимый
  диалог: `{"checkpointId": N}` → `{"dialogId", "title"}`. Записи до границы
  копируются, факты разворачиваются из снимка, настройки сохраняются записью вида
  `settings` (страница применяет их при восстановлении). Указатель «текущего диалога»
  форк не трогает — ветка открывается вкладкой в полосе над чатом (или вручную через
  `chat_agent.html?dialog=<id>`).
- `GET /api/agent/history` принимает необязательный `?dialog=<id>` — без него
  восстанавливается текущий диалог (старый режим), с ним — указанный (ветка в новой
  вкладке).

## 6. Агент (`chat_agent.html` + пакет `agent`)

### 6.1. Протокол вызова инструментов (`AgentProtocol`)

Function calling эмулируется текстовым протоколом: системный промпт описывает
инструменты, модель отвечает строго одним JSON-объектом
`{"tool": "<имя>", "args": {...}}` или массивом до 5 таких объектов (независимые вызовы
выполняются параллельно на виртуальных потоках). Любой другой ответ — финальный ответ
пользователю.

Устойчивость к слабым моделям:

- толерантный JSON-парсер (неэкранированные переводы строк, одинарные кавычки,
  висячие запятые), снятие ```` ```json ````-ограждений;
- починка типичных повреждений: потерянная открывающая `{` и/или кавычка ключа `tool`;
- извлечение сбалансированных `{...}`-объектов с полем `tool` из окружающей прозы
  (проза показывается пользователю отдельно);
- детектор «похоже на вызов инструмента, но не парсится» (`looksLikeToolCall`): такой
  ответ не показывается как обычный, а возвращается модели как ошибка протокола;
  после 3 подряд повреждённых ответов ход завершается;
- при обрезке ответа лимитом токенов (`finish_reason=length`) обрывочный «хвост»
  (незакрытый fence / незакрытый `{`) срезается, пользователю показывается
  предупреждение с кнопкой «Сжать контекст».
- Каждый вызов валидируется до исполнения: имя инструмента, обязательные поля, типы,
  лимиты (имя файла ≤ 255 символов, content ≤ 100 000 символов, expression ≤ 1000
  символов и только `0-9 + - * / % ^ ( )`).

### 6.2. Инструменты (`AgentTools`)

Все файловые операции — в песочнице `test/`: принимаются только простые имена файлов
(без разделителей путей, `..`, двоеточий), итоговый путь перепроверяется на вхождение
в корень песочницы.

| Инструмент | Аргументы | Подтверждение |
|---|---|---|
| `get_system_time` | — | нет |
| `list_files` | — | нет |
| `read_file` | `name` | нет (чтение обрезается до 20 000 символов) |
| `write_file` | `name`, `content` | **да** |
| `append_file` | `name`, `content` | **да** |
| `delete_file` | `name` | **да** |
| `calculate` | `expression` | нет (безопасный парсер: числа, `+ - * / % ^`, скобки) |
| `update_plan` | `steps[]` | нет (внутренний: обновляет видимый план, файлов не трогает) |

Мутирующие операции требуют явного разрешения пользователя на каждую операцию
(запрос с предпросмотром содержимого, таймаут 5 минут = отказ).

### 6.3. Сессия агента (`AgentSession`)

Цикл хода: сообщение пользователя → фаза планирования (отдельный LLM-вызов, план из
1–7 шагов приходит строгим JSON, токены не стримятся в чат) → цикл «LLM → вызов(ы)
инструментов → результаты обратно в контекст» до финального текстового ответа.

Возможности и ограничения:

- **Планирование** — отключаемо; план отображается в UI и обновляется инструментом
  `update_plan`; все шаги помечаются done при финальном ответе.
- **Лимит вызовов инструментов подряд** (по умолчанию 5, максимум 50) — не жёсткая
  остановка: у пользователя спрашивают, продолжать ли.
- **Пауза / продолжение / прерывание**: пауза срабатывает между шагами; abort
  немедленно закрывает активное HTTP-соединение к LLM и разблокирует ожидания
  разрешений.
- **Сжатие контекста** — пять режимов:
  - `none` — вся история;
  - `lastN` — последние N пользовательских/assistant-сообщений (считаются только они;
    записи инструментов остаются при своём ходе; окно не начинается с середины хода);
  - `sliding` — жёсткое скользящее окно: последние N записей истории любого типа
    (включая результаты инструментов), всё старое отбрасывается; окно может начаться
    с середины хода;
  - `sticky` — **Sticky Facts / Key-Value Memory**: факты извлекаются отдельными
    вызовами LLM без контекста (из сообщения пользователя — до хода, из финального
    ответа ассистента — после), сохраняются в БД с upsert по нормализованному ключу
    (нижний регистр, ё→е), категории goal/constraint/preference/decision/fact;
    в контекст подаётся блок фактов + последние `stickyKeep` сообщений. Лимит
    `factsMax` с LRU-вытеснением; при `factsConsolidate > 0` каждые M сообщений
    LLM сливает дубли и противоречия списка фактов;
  - `summary` — старая часть заменяется LLM-сводкой, хранящейся отдельно от истории;
    сводка перегенерируется пакетами по `summaryEvery` сообщений, последние `summaryKeep`
    остаются дословно; при сбое — повтор с пакетом из 2 сообщений, далее — предупреждение
    в чат и продолжение со старой сводкой.
- **Нормализация ролей** перед отправкой в LLM (`normalizeRoles` в `buildMessages`):
  итоговый список сообщений приводится к строгому чередованию user/assistant, требуемому
  chat-шаблонами (LM Studio): подряд идущие сообщения одной роли сливаются в одно
  (summary-блок/блок фактов + первое user-сообщение окна, несколько tool-записей подряд),
  а если диалог начинался бы с assistant-сообщения (окно `sliding` началось с середины
  хода), в начало вставляется нейтральный user-маркер «(продолжение диалога)».
- **Контроль заполнения контекстного окна**: при известном `context-window` модели
  предупреждения в чат на 85 % и 95 % заполнения (перевзводятся при падении ниже 80 %),
  на 95 % предлагается кнопка включения сжатия.
- **Режим без инструментов** (`tools: false`) — чистый чат: протокол инструментов
  не применяется, любой ответ — финальный (используется скриптами диалогов).
- **Статистика**: токены каждого вызова, накопительный счётчик токенов диалога,
  число LLM-вызовов и вызовов инструментов за ход, длительность хода.

### 6.4. Персистентность диалогов агента (`AgentDialogStore`)

SQLite, схема готова к мультидиалоговости:

- `agent_dialogs(id, title, created_at, updated_at)` — диалоги;
- `agent_dialog_entries(id, dialog_id, kind, payload, created_at)` — записи двух типов:
  UI-транскрипт (`user`, `assistant`, `prose`, `tool`, `plan`, `permission`, `note`,
  `reply_error`, `usage`, `turnstats`, `summary`, `facts`, `settings`) для перерисовки
  чата и восстановления состояния на границе checkpoint'а, и `history`
  ({role, content}) для восстановления LLM-контекста;
- `agent_facts(id, dialog_id, category, key_norm, key_display, value, updated_at)` —
  key-value память режима sticky (UNIQUE по `(dialog_id, key_norm)`);
- `agent_checkpoints(id, dialog_id, label, entry_id, state_json, created_at)` —
  снимки диалога для ветвления: `entry_id` — граница копирования записей,
  `state_json` — список фактов и настройки панели на момент снимка;
- `agent_state(key, value)` — указатель на текущий диалог.

После перезапуска приложения страница агента восстанавливает текущий диалог целиком
(транскрипт + контекст + счётчик токенов + сводка + статусная строка последнего хода),
и диалог можно продолжить. «Новый диалог» снимает указатель, но хранимый транскрипт
сохраняется для будущего списка диалогов.

## 7. Веб-интерфейс и фронтенд

### 7.1. Общие принципы фронтенда

Три статические страницы (`web/index.html`, `web/batch.html`, `web/chat_agent.html`) —
vanilla HTML/CSS/JS в одном файле каждая: без сборки, без фреймворков, без внешних
библиотек и CDN. Сервер отдаёт их как статику из `web/`.

**Раскладка.** Одинаковая на всех страницах: контейнер до 1400 px по центру, шапка
с заголовком и навигационными ссылками между режимами, двухколоночный layout —
чат слева (резиновый), липкая панель настроек справа (380 px, собственная прокрутка).
Медиазапрос на 900 px переключает раскладку в одну колонку (настройки уходят под чат).

**Дизайн-система.** Серый фон `#f0f2f5`, белые карточки с радиусом 10 px, основной
акцент — синий `#2563eb`; системный шрифтовой стек. Пузыри сообщений: пользователь —
синий справа, ассистент — серый слева, ошибки — красноватые, служебные заметки —
мелкий серый текст по центру. Подчинённые поля настроек (описание формата, max_tokens
и т. п.) скрываются/показываются в зависимости от выбранной радиокнопки.

**Чтение SSE-потока.** Все страницы используют один приём: `fetch()` +
`resp.body.getReader()` + `TextDecoder` (EventSource не используется — нужен POST
с JSON-телом). Буфер разбирается по разделителю `\n\n`, каждый кадр парсится
функцией `parseSseEvent` (`event:` + `data:`); данные внутри кадра — JSON.
Идентичный код разбора продублирован на трёх страницах.

**Мини-Markdown-рендерер.** Собственный построчный рендерер (~110 строк, продублирован
на всех страницах): сначала экранирует HTML, затем обрабатывает fenced code blocks,
таблицы (строка `|` + строка-разделитель `---`), заголовки `#`–`####`, цитаты,
горизонтальные линии, маркированные/нумерованные списки и инлайн-разметку
(`**bold**`, `*italic*`, `` `code` ``, ссылки). Пока ответ стримится, пузырь
показывает сырой текст; Markdown применяется один раз в конце стрима (на странице
агента — на каждый токен, чтобы проза вокруг вызовов инструментов сразу выглядела
оформленной).

**Диагностика ошибок фронтенда.** На всех страницах глобальные обработчики
`window.onerror` и `unhandledrejection` выводят JS-ошибки прямо в чат красным
пузырём — сбой интерфейса не проходит незамеченным.

### 7.2. `index.html` — чат (1325 строк)

**Панель настроек.** Шесть fieldset-групп: модель (список из `/api/models`),
формат ответа (7 вариантов с полями описания), stop sequence (естественная
остановка / max_tokens / пользовательские последовательности), парсинг ответа
(JSONPath/XPath + выражение), глубина размышлений (default/low/high/max),
температура (none/custom 0–2), контекст диалога (чекбокс + лимит в токенах +
кнопка «Новый диалог»). Функция `collectSettings()` собирает форму в объект
настроек, который целиком подмешивается в тело запроса `/api/chat`.

**Пресеты.** Список загружается из `/api/presets` и группируется в `<optgroup>`
«Мои наборы» / «Примеры». Применение пресета заполняет форму (`applySettings`);
если пресет ссылается на модель, которой нет в текущем списке, она добавляется
в селект как новый пункт. «Сохранить» — upsert по имени через `prompt()`,
«Удалить» — с `confirm()`. Статусные сообщения зелёные/красные, самозатухающие
через 4 с.

**Отправка сообщения.** Пузырь пользователя появляется сразу, затем пузырь
«Думаю…» с посекундным счётчиком ожидания до первого токена. Обработка
SSE-кадров:

- `token` — дописывается в пузырь ответа (сырой текст, автоскролл);
- `reasoning` — складывается в сворачиваемый `<details>`-блок «Размышления модели
  (N зн.)» над пузырём ответа;
- `conversation` — сохраняет `conversationId` в `localStorage` (режим контекста);
- `context` — выводит серую заметку «Контекст: отправлено X из Y сообщений…»;
- `done` — финализация: Markdown-рендер пузыря, строка метаданных под ним
  (применённая модель/формат/max_tokens/стоп-последовательности/размышления/
  температура, контекст «N из M сообщений», время, токены prompt+completion
  (+reasoning) = total, finish_reason), при необходимости — пузырь результата
  парсинга (зелёный, моноширинный) или ошибки парсинга;
- `error` — пузырь заменяется сообщением об ошибке.

Отдельно обрабатывается случай пустого ответа с `finish_reason=length`:
показывается подсказка, что reasoning-токены съели бюджет max_tokens.

**Строка статуса под чатом.** Накопительный счётчик потраченных токенов (включая
вспомогательные вызовы суммаризации, `auxTokens`) и состояние контекстного окна.
Счётчик и `conversationId` хранятся в `localStorage` — переживают перезагрузку
страницы; «Новый диалог» сбрасывает оба и удаляет диалог на сервере
(`DELETE /api/conversations`).

**Восстановление.** При загрузке страницы, если в `localStorage` есть
`conversationId`, история запрашивается с сервера и перерисовывается (ответы
ассистента проходят Markdown-рендер); неизвестный id молча забывается.

**Контекстное меню.** Правый клик по пузырю пользователя — «Повторить с текущими
настройками»: тот же текст отправляется заново с актуальными значениями формы.

### 7.3. `batch.html` — пакетный режим (1162 строк)

**Формат задания.** JSON-файл загружается через `<input type="file">` и валидируется
на клиенте с детальными сообщениями об ошибках: `{"tasks": [{"name",
"messages": [варианты формулировок], "expectedAnswer"?: "...", "settingsGroups":
[{"name", "settings"}]}]}` (поддерживаются legacy-поля `message` и `settings`).
Каждая комбинация «задача × формулировка × набор настроек» — одно выполнение.
Перед запуском — подтверждение с числом задач и выполнений.

**Исполнение.** Пул из 40 параллельных воркеров (`PARALLEL_WORKERS`) разбирает
общую очередь выполнений; каждое выполнение — обычный POST `/api/chat` со стримом
(токены накапливаются, но не отображаются). Кнопка «Прервать» дёргает
`AbortController` — активные запросы обрываются, частичные результаты сохраняются.
Прогресс каждого выполнения пишется серой строкой в чат («Выполнение … готово
(N с, M токенов)»). При включённом контексте каждая задача получает свой
изолированный диалог на сервере (без `conversationId` в запросе), который
удаляется сразу после выполнения.

**Проверка ответов.** Если задан `expectedAnswer`, ответ сверяется эвристикой:
нормализация (нижний регистр, ё→е, схлопывание пробелов) + вхождение подстроки;
если эталон содержит числа — достаточно, чтобы все числа присутствовали в ответе
(устойчиво для числовых головоломок).

**Таблица результатов.** Колонки: задача, вариация, набор настроек, ожидаемый
ответ, ответ, время, токены, стоимость (колонки без данных скрываются); строка
«Итого». Стоимость считается на клиенте по тарифам из `/api/models`
(`pricePrompt`/`priceCompletion`); для моделей без цены — оценка по самому
дёшевому тарифу из конфига с маркером «≈». Кнопки: «Экспорт CSV» (разделитель `;`,
BOM для русского Excel) и «Анализ результирующей таблицы».

**LLM-анализ.** Клиент сам агрегирует статистику (точность, время min/avg/max,
токены, стоимость — по наборам настроек и по вариациям формулировок), собирает
список ошибочных ответов и «креативные» задачи с подсчётом уникальных ответов,
формирует структурированный промпт аналитику и отправляет его на `/api/chat` с
`useCloud: true` (модель анализа). Ответ стримится с живым Markdown-рендером;
после завершения доступна кнопка «Экспорт анализа (MD)». Примеры файлов заданий:
`batch-example.json`, `batch-hard-puzzles.json`, `batch-logic-puzzles.json`,
`batch-number-puzzles.json`, `batch-temperature-example*.json`.

### 7.4. `chat_agent.html` — агент (2103 строки)

**Панель настроек.** Сжатие контекста (none / lastN+N / sliding+N / sticky+N+макс. фактов+консолидация / summary+N keep+M every),
панель «Память диалога» (текст текущей сводки + список известных фактов с категориями
и счётчиком), лимит вызовов инструментов подряд,
чекбокс планирования, «Новый диалог», загрузка скрипта диалога. Выбранный режим
сжатия и его числовые параметры сохраняются в `localStorage` и восстанавливаются
при перезагрузке; неактивные поля задизейблены.

**Индикация работы.** Под областью чата — закреплённая «полоса печати» (typing bar)
с анимированными точками и текстом текущей фазы («Агент думает…», «Составляю
план…», «Выполняется инструмент: read_file…», «Ожидается ваше решение…»). Ниже —
два ряда чипов: токеновые (весь запрос с раскладкой вход/выход, отдельно токены
финального ответа, накопительный счётчик за диалог) и процессные (число
LLM-вызовов и вызовов инструментов, контекст «kept/total сообщ.», покрытие
summary, заполнение окна модели в % — жёлтый с 85 %, красный с 95 %, длительность
хода, метка «прервано»).

**Обработка SSE-событий агента** (главный цикл `runTurn`):

- `session` — запоминается id сессии для последующих ходов и команд управления;
- `planning` / `plan` — плейсхолдер «📋 Составляю план…» (анимация точек) сменяется
  блоком плана с иконками статусов (⏳ pending, 🔄 in_progress, ✅ done — зачёркнут);
  блок обновляется при каждом `update_plan`;
- `reasoning` — поток «мышления» в открытый `<details>`-блок «🧠 Мышление»
  (пустые whitespace-фрагменты отбрасываются; по завершении блок сворачивается,
  а совсем пустой — удаляется);
- `token` — стрим в пузырь ответа с живым Markdown-рендером на каждый токен;
- `tool_call` — если модель обернула вызов в прозу, проза показывается обычным
  пузырём; частично отрендеренный JSON вызова заменяется аккуратным
  `<details>`-блоком «🔧 имя аргументы» со статусом «выполняется…»;
- `tool_result` — блок заполняется результатом (красная рамка при ошибке);
- `reply_error` — повреждённый вызов инструмента показывается красным
  сворачиваемым блоком (сырой текст доступен внутри), статус «повторная попытка
  N/3»;
- `reply` — замена пузыря очищенным текстом при серверной обрезке обрывочного
  хвоста после лимита токенов;
- `permission_request` / `limit_confirm` — жёлтый пузырь решения с кнопками
  «Разрешить/Запретить» (с предпросмотром содержимого файла) или
  «Продолжить/Остановить»; решение уходит POST `/api/agent/permission`;
  `permission_resolved` превращает пузырь в итоговую строку «✅ Разрешено…» /
  «⛔ Запрещено…»;
- `note` — предупреждения; при `offerCompression` рядом появляется кнопка
  «Сжать контекст», переключающая радиокнопку в настройках и шлющая
  `/api/agent/control` с `action: "compress"`;
- `summary` — обновление панели «Память диалога» (сводка);
- `facts` — обновление панели «Известные факты» (режим sticky): полный список фактов;
- `paused` / `resumed` — переключение кнопки «Пауза»/«Продолжить»;
- `done` — рендер чипов статистики хода и счётчика диалога; если стрим закрылся
  без `done` (рестарт сервера, обрыв) — ввод разблокируется с пояснением вместо
  зависания;
- `error` — красный пузырь с текстом ошибки.

**Управление ходом.** Пока ход активен, видны кнопки «Пауза» и «Прервать»
(`/api/agent/control`), ввод заблокирован. «Новый диалог» — `DELETE
/api/agent/session`, полная очистка чата, чипов и панели памяти.

**Восстановление после перезапуска.** При загрузке страница запрашивает
`GET /api/agent/history` и перерисовывает весь диалог по записям транскрипта:
пузыри user/assistant (с Markdown), проза вокруг вызовов, свёрнутые блоки
инструментов с результатами, блок плана, итоги разрешений, заметки, повреждённые
ответы; отдельно восстанавливаются счётчик токенов диалога, панель сводки и
чипы последнего хода (`renderHistoryEntry`). Параметр URL `?dialog=<id>` загружает
конкретный диалог вместо текущего (используется и полосой вкладок, и при ручном
открытии диалога в отдельной вкладке браузера); если у диалога есть запись `settings` (оставлена форком), она применяется
к панели настроек через `applyDialogSettings`.

**Checkpoints (ветвление диалога).** При наведении на пузырь пользователя на правом
поле чата появляется SVG-иконка ветвления (без рамки, hover-only, не перекрывает
текст) — она сохраняет checkpoint на конце этой пары вопрос-ответ
(`POST /api/agent/checkpoint` с параметром `turn`; пузыри нумеруются при рендере,
сервер считает ходы по записям `user`) и СРАЗУ форкает его
(`POST /api/agent/checkpoint/fork`): ветка появляется вкладкой над чатом и становится
активной, исходный диалог тоже получает вкладку. Ветка получает автоимя
«Ветка · после пары N», переименование — двойным кликом по вкладке (inline).
Отдельного списка checkpoint'ов в панели нет — ветвление управляется маркерами
и вкладками. Ветка — полностью независимый диалог:
записи до границы скопированы, дальнейшие ходы пишутся только в неё. Факты при
каждом обновлении журналируются записями `facts` в транскрипт — это позволяет
восстановить список фактов на момент любого checkpoint'а, а не только текущий.

**Вкладки диалогов.** Над чатом — полоса вкладок (`#dialogTabs`), видна только
когда диалогов больше одного. Вкладка — `{id, title}` в `localStorage`
(`agentDialogTabs`), название по умолчанию — «Диалог»; активная подсвечена, ✕
закрывает вкладку (диалог в БД остаётся). Переключение stateless:
`clearChatUi` + `GET /api/agent/history?dialog=<id>` — сервер возвращает и `title`
(он же приходит в SSE-событии `session`, вкладка появляется автоматически при
первом ходе нового диалога; у диалогов скрипта вкладка называется именем диалога
из файла). Переключение и закрытие заблокированы во время хода
или прогона скрипта (`busy`/`scriptActive` — иначе стрим токенов ушёл бы в чужой
чат). «Новый диалог» превращает активную
вкладку в пустой диалог. Параметр URL `?dialog=<id>` по-прежнему открывает
конкретный диалог (например, в отдельной вкладке браузера).

**Скрипты диалогов.** JSON-файл `{"dialogs": [{"name", "settings", "messages": [...]}]}`
валидируется при выборе; запуск прогоняет диалоги последовательно: перед каждым —
свежая сессия (`DELETE` старой) и полная очистка чата (`clearChatUi`: сообщения,
панели сводки и фактов, чипы процесса и токенов), каждый диалог получает вкладку
над чатом с именем из файла, так что после прогона доступны все, а не только
последний; настройки диалога применяются к
элементам панели (флаг `tools` держится отдельно в `toolsOverride`, контрола для
него нет). Ввод заблокирован на весь прогон (`scriptActive`); прерывание хода
останавливает и скрипт. После каждого диалога агрегируются токены, LLM-вызовы,
вызовы инструментов, длительность и пары «вопрос → последний ответ ассистента».
По окончании — сравнительная таблица «метрика × диалог» с зелёной/красной
подсветкой min/max, кнопки «Экспорт CSV» и «Анализ (модель для анализа)»:
промпт с перепиской всех диалогов уходит на `/api/chat` с `useCloud: true`,
ответ стримится с Markdown-рендером и доступен для выгрузки в .md.
Таблица и анализ живут в отдельном контейнере `#scriptResults` под рамкой чата
(не внутри `#chat`), поэтому переключение вкладок и очистка чата их не стирают;
при новом прогоне контейнер очищается. Результаты привязаны к диалогу, из
которого запущен скрипт: видны только на его вкладке
(`updateScriptResultsVisibility`), после прогона страница сама возвращается
на эту вкладку.

## 8. Хранение данных

Один файл SQLite `settings.db` (в `.gitignore`), три независимых хранилища:

| Таблица | Назначение |
|---|---|
| `presets(id, name UNIQUE, settings, is_default, created_at)` | пресеты настроек чата |
| `conversations(id, summary, summary_upto, created_at, updated_at)` | диалоги чата + сводка |
| `messages(id, conversation_id, role, content, created_at)` | сообщения диалогов чата |
| `agent_dialogs(id, title, created_at, updated_at)` | диалоги агента |
| `agent_dialog_entries(id, dialog_id, kind, payload, created_at)` | транскрипт + история агента |
| `agent_facts(id, dialog_id, category, key_norm, key_display, value, updated_at)` | key-value память (режим sticky) |
| `agent_checkpoints(id, dialog_id, label, entry_id, state_json, created_at)` | снимки диалога агента для ветвления |
| `agent_state(key, value)` | указатель на текущий диалог агента |

## 10. Известные ограничения и roadmap

Зафиксированы в `agent-improvements.md`:

- **Критично:** долговременная память между сессиями агента; самокоррекция/рефлексия
  после ошибок инструментов; перепланирование при нерабочем плане.
- **Важно:** переход с текстового JSON-протокола на нативный function calling
  (поле `tools` OpenAI API); общий бюджет задачи (шаги/токены/время); потоковый план.
- **Следующий уровень:** новые инструменты (веб-поиск, HTTP, выполнение кода, git);
  политики подтверждений вместо точечных запросов; sub-агенты; метрики успешности агента.

Прочее: оценка токенов в чате приблизительная (~3 символа/токен), без реального
токенизатора; сессии агента в памяти (восстанавливаются из БД по требованию); UI
агента пока поддерживает один текущий диалог (схема БД — мультидиалоговая).
