# План: страница `/v2/agent.html` — агент с явной моделью памяти (memory layers)

**Статус:** реализовано. Разделы 5 и 8 приведены к фактической реализации; основные
сценарии проверены на изолированной SQLite БД и mock LLM.

## 1. Цель и отличие от текущей страницы агента

Новая страница `web/v2/agent.html` (раздаётся существующим статическим обработчиком
`ChatServer.handleStatic`, путь `/v2/agent.html` → `web/v2/agent.html`). Существующая
`chat_agent.html` остаётся нетронутой: v2 — отдельный UI и отдельный backend-контур,
но переиспользует `LlmClient`, SSE-механику и наработки `AgentSession`.

Главное отличие: память — не «побочный эффект сжатия», а **явная сущность**:
три слоя с собственными таблицами, правилами попадания в промпт, токенным учётом,
редактированием и очисткой. Всё, что уходит в LLM, видно пользователю as is.

## 2. Раскладка страницы (4 панели)

```
┌───────────────────────────────────────────────┬──────────────────────┐
│  C. Настройки — НАД ЧАТОМ                     │  D. Состояние агента │
│  основная модель, модель анализа,             │  - системный промпт  │
│  сжатие ST + параметры, planning, tools       │    (только чтение)   │
├───────────────────────────────────────────────┤  - память: 3 слоя,   │
│  A. Чат (по chat_agent.html)                  │    токены каждого,   │
│  пузыри, инструменты, план, typing bar,       │    редактировать/   │
│  чипы токенов/хода                            │    очистить          │
│  [Пауза/Продолжить] [Прервать]                │  - журнал LLM:       │
├───────────────────────────────────────────────┤    сворачиваемый     │
│  B. Ввод запроса (по chat_agent.html)         │    список всех       │
│  textarea + «Отправить», Enter/Shift+Enter,   │    запросов/ответов  │
│  блокировка во время хода                     │    as is             │
│  Под вводом: «Загрузить диалог» (скрипт),     │  - лог действий      │
│  «Анализ диалога», «Анализ скрипта»           │    пользователя      │
└───────────────────────────────────────────────┴──────────────────────┘
```

- A/B/C берутся из `chat_agent.html` (разметка + `runTurn`/SSE-парсер). C — компактная
  горизонтальная панель над чатом: отдельные выпадающие списки **основной модели** и
  **модели анализа**, затем настройки сжатия ST, planning и tools. Числовые параметры
  группируются в одну строку, длинные подсказки — в tooltip'ы.
- Все элементы настройки C, включая оба выбора модели, блокируются на время хода агента,
  прогона скрипта и анализа (`disabled` у общего `fieldset`). После `done`, `error` или
  прерывания настройки разблокируются. Кнопки паузы и прерывания находятся вне этого
  `fieldset` и остаются доступными во время выполнения.
- Основная модель используется для ответов агента и служебных вызовов памяти; модель
  анализа — для «Анализа диалога» и «Анализа скрипта». Выбор модели анализа передаётся
  в запрос явно, а не только через скрытый серверный `llm.analysis.model`.
- D — новая панель-инспектор, справа, со вкладками или `<details>`-секциями.

### 2.1. Пауза и отмена текущего действия

В v1 нужные механизмы уже есть и проверены по коду: `POST /api/agent/control` вызывает
`AgentSession.pause()/resume()/abort()`, UI имеет кнопки «Пауза»/«Прервать» и обрабатывает
SSE `paused`/`resumed`. В v2 они переносятся без изменения базовой семантики:

- **Пауза** действует между шагами агента: текущий LLM-вызов завершается, затем поток
  останавливается перед следующим шагом. До события `paused` UI показывает
  «Пауза после текущего шага», кнопка меняется на «Продолжить» после остановки.
- **Прервать** отменяет текущее действие: закрывает активный LLM-поток, снимает паузу,
  разблокирует ожидания permission/limit и завершает ход с `done.aborted=true`.
  При прогоне скрипта прерывается текущий ход и последующие диалоги/сообщения не запускаются.
- Во время паузы настройки остаются заблокированными; доступны «Продолжить» и «Прервать».
- Пауза, продолжение и прерывание фиксируются в логе действий пользователя.

## 3. Модель памяти

### 3.1. Слои и содержимое

| Слой | Что хранит | Время жизни | Источник наполнения |
|---|---|---|---|
| **short-term** | текущий диалог: история сообщений и извлечённые sticky-факты; к истории применяются **варианты сжатия** (см. 3.2) | диалог | история ходов + служебные вызовы сжатия |
| **working** | активная задача: формулировка, критерии приёмки, ограничения, план/статус, промежуточные результаты и артефакты | задача; сброс при явном завершении/смене задачи | сообщения пользователя + обновление по ходу + ручная правка |
| **long-term** | **конфиг агента**: устойчивые инструкции, роль и правила поведения, требования к формату ответов и использованию инструментов; без фактов конкретного пользователя, задачи или диалога | глобально, между всеми задачами и диалогами; **никогда автоматически не урезается** | только явное редактирование пользователем |

Sticky-факты остаются частью **short-term** и принадлежат конкретному диалогу.
Они включаются отдельным чекбоксом `stickyFacts` независимо от сжатия истории;
по умолчанию включены. Они не переносятся в long-term: долговременный слой в v2 —
это конфигурация агента, а не хранилище сведений о пользователе или задачах.

### 3.2. Сжатие — только short-term

К истории short-term применимы `none` (вся история), `lastN` (последние N реплик),
`sliding` (жёсткое окно последних N записей), `summary` (сводка + последние N).
При включённом `stickyFacts` блок фактов добавляется к любому из этих режимов.
Старый API-режим `compression=sticky` поддерживается для совместимости как lastN +
факты. Использованные настройки фиксируются в журнале каждого LLM-запроса.

Working и long-term **не сжимаются и не урезаются** — ни по числу записей, ни по
токенам. Если оценка запроса превышает окно модели, деградация касается только ST
(уменьшение N / принудительный summary) с предупреждением пользователю. Если даже
пустой ST не помогает, запрос блокируется с понятной ошибкой: LT и WT не обрезаются
молча.

### 3.3. Правила попадания в промпт (у каждого слоя — явное)

| Слой | Правило | Параметр |
|---|---|---|
| short-term | история после применения выбранного режима сжатия | режим + `stMessages`/`stSummaryKeep`/`stSummaryEvery` |
| working | все данные активной задачи; если активной задачи нет — слой пуст и в промпт не идёт | без лимитов и top-K |
| long-term | весь конфиг агента целиком в каждом основном запросе | без лимитов, top-K и выборки по релевантности |

Формат в контексте: каждый слой — отдельный помеченный блок
(`[LONG-TERM]`, `[WORKING]`, `[SHORT-TERM]`), сборка в `MemoryAssembler`.
Порядок: system → long-term/config → working → short-term (сжатая история) →
текущий запрос пользователя.

### 3.4. Варианты подгрузки памяти

1. **Фиксированная сборка (MVP)**: LT и WT идут целиком, ST — после выбранного
   пользователем сжатия. Это основной и наиболее предсказуемый вариант.
2. **Адаптивный бюджет ST**: перед запросом резервируются токены под system, полный LT,
   полный WT, текущий запрос и ответ модели; остаток окна отдаётся ST. При нехватке
   места автоматически уменьшается N или включается summary, а событие попадает в журнал.
3. **Только активная задача из WT**: если пользователь ведёт несколько задач, в промпт
   попадает полный набор данных только выбранной активной задачи; остальные задачи
   хранятся в БД, но не подгружаются. Это переключение задачи, а не урезание её данных.

MVP = вариант 1 с обязательной проверкой переполнения; вариант 2 — следующий шаг.
Вариант 3 добавляется только если подтверждена работа с несколькими задачами в одном
диалоге.

### 3.5. Токенный учёт по слоям

Точной токенизации на стороне LM Studio/OpenAI-совместимого API нет, поэтому:

- `TokenEstimator`: эвристика `ceil(chars / 3)` для русского текста, калибруется
  по фактическому `usage.prompt_tokens` ответа (после ответа показываем
  «оценка vs факт» и поправочный коэффициент сохраняем в настройках).
- При сборке промпта `MemoryAssembler` возвращает не только сообщения, но и
  **разбивку**: `{system, longTerm, working, shortTerm, user} → chars, estTokens`.
- UI: чипы в панели D «ST ~120 t · WT ~80 t · LT ~250 t · всего ~N t»;
  в журнале LLM у каждого запроса сохраняется та же разбивка + фактические usage,
  включая `reasoningTokens`, если их предоставил провайдер.
- В метриках конкретного хода «Вход», «Выход» и «Всего» суммируют prompt, completion и их сумму
  по всем успешным LLM-вызовам хода: `working_update`, `extract_st`, `planning`, `summary`, все
  основные `chat` и извлечение фактов из финального ответа. Reasoning-токены входят в completion
  usage и не добавляются повторно. Usage неудачного запроса доступен только если его вернул
  провайдер. Нижняя панель отдельно суммирует эти метрики по всем ходам видимого чата.

### 3.6. Редактирование и очистка

- Панель D, секция каждого слоя: просмотр, редактирование и «Очистить слой»
  с подтверждением. Все операции — через API и попадают в лог действий.
- **short-term:** отдельные сводка и компактный прокручиваемый список sticky-фактов
  с иконками категорий, подсказками, добавлением и удалением. Двойной клик открывает
  редактирование, сохранение автоматическое; очистка всех фактов выполняется отдельно
  с подтверждением. Исходный JSON доступен в сворачиваемом блоке.
  Режим сжатия выбирается в настройках, очистка истории диалога доступна отдельно; исходные
  сообщения истории не редактируются.
- **working:** редактируемые поля формулировки задачи, критериев приёмки, ограничений,
  статуса, результатов и заметок; отдельные действия «Завершить задачу» и «Очистить».
- **long-term:** список типизированных правил с добавлением, редактированием, удалением
  и режимом просмотра исходного JSON; никаких pin/top-K, автоматической консолидации
  или вытеснения записей.
- Отдельная кнопка **«Сбросить всё»** с подтверждением очищает оперативную память
  ST/WT всех диалогов и глобальный LT. Транскрипты, статистика ходов `turnstats`, накопленные
  `usage`, журналы LLM и действий сохраняются для аудита и восстановления общих метрик;
  в подтверждении явно указано глобальное действие кнопки.

### 3.7. Согласованные решения для MVP

- **LT:** JSON со списком типизированных правил. Формат:
  `{"rules": [{"id", "type", "text"}]}`. Начальные типы: `role`, `behavior`,
  `output_format`, `tool_policy`, `constraint`, `custom`. Порядок правил сохраняется,
  весь массив без выборки передаётся в каждый основной запрос. Backend проверяет
  корректность JSON, уникальность `id` и непустой `text`.
- **WT:** автоматическое обновление через отдельный LLM-вызов + ручная правка.
  Служебный вызов получает только текущий WT и новое сообщение пользователя, без всей
  истории диалога. Возвращается инкрементальный patch с операциями `set` / `append` /
  `remove`; если сообщение не меняет задачу — `changed=false`. Полный JSON не
  перегенерируется, неизменённые поля не занимают completion-токены.
- **Новая задача:** кнопка «Новая задача» создаёт новый диалог с чистыми WT и ST;
  глобальный LT сохраняется. Автоматического определения смены темы в MVP нет.
- **Полный сброс:** кнопка «Сбросить всё» с подтверждением очищает все три слоя памяти,
  но не удаляет транскрипты и журналы.
- **ST:** режимы истории — `none`, `lastN`, `sliding`, `summary`; sticky-факты —
  независимый чекбокс, по умолчанию включён. Старый `compression=sticky` поддерживается
  для совместимости со скриптами.
- Несколько одновременно активных задач в одном диалоге в MVP не поддерживаются.

## 4. Хранение (SQLite, тот же `settings.db`, префикс `v2_`)

| Таблица | Назначение |
|---|---|
| `v2_dialogs(id, title, created_at, updated_at)` | диалоги v2 |
| `v2_entries(id, dialog_id, kind, payload, created_at)` | транскрипт + `history` (как в v1) |
| `v2_facts(id, dialog_id, key_norm, key_display, value, updated_at)` | sticky-факты short-term, строго в рамках диалога |
| `v2_working(dialog_id, field, value, updated_at)` | все данные активной задачи |
| `v2_agent_config(id, content, updated_at)` | long-term: глобальный JSON с типизированными правилами агента, singleton, без `dialog_id` |
| `v2_llm_log(id, dialog_id, kind, request_json, response_text, reasoning_text, layer_stats_json, usage_json, duration_ms, created_at)` | все запросы/ответы и размышления as is; колонка reasoning добавляется миграцией в существующих БД |
| `v2_action_log(id, dialog_id, action, details_json, created_at)` | действия пользователя |
| `v2_state(key, value)` | указатель текущего диалога, калибровка токенов |

`v2_agent_config.content` хранит JSON с полным массивом правил, который без сокращений
попадает в каждый основной запрос. `v2_llm_log.kind`: `chat`, `extract_st`,
`working_update`, `summary` — отдельные служебные вызовы тоже логируются
(as is, с входом и выходом).

## 5. Backend

Новый пакет `agent.v2` (или подпакет классов в `agent`):

- `AgentV2Session` — цикл хода по образцу `AgentSession`: user → обновление working
  и/или sticky-фактов ST (если включено) → сборка контекста → LLM (инструменты/план —
  опционально, как в v1) → ответ → логирование. Поддерживает `pause()/resume()/abort()`
  и отслеживание активного LLM-соединения.
- `MemoryStore` — CRUD и очистка трёх слоёв; для LT — чтение/сохранение полного
  конфига агента, без автоматической консолидации и вытеснения. Журналы LLM и действий
  также записываются через это хранилище.
- `MemoryAssembler` — токенная разбивка по слоям для каждого LLM-запроса.
- `TokenEstimator` — оценка + калибровка по фактическим usage.

Реализованные эндпоинты (отдельные от v1):

- `POST /api/v2/agent/chat` — ход, SSE (`session`, `token`, `memory` (снимок слоёв+токены),
  `llm_call` (id записи журнала), `paused`, `resumed`, `done`, `error` …);
- `POST /api/v2/agent/control` — `{sessionId, action: pause|resume|abort}`; управление
  текущим ходом, включая прерывание активного LLM-запроса;
- `GET /api/v2/agent/history?dialog=` — восстановление;
- `POST /api/v2/agent/dialog/new` — новая задача: новый диалог с чистыми ST/WT;
- `GET/PUT/DELETE /api/v2/agent/memory?layer=st|wt|lt&dialog=` — чтение/редактирование/очистка
  слоёв; `dialog` обязателен для ST/WT, если не выбран текущий диалог;
- `POST /api/v2/agent/reset` — подтверждённый глобальный сброс ST/WT/LT с сохранением
  транскриптов и журналов;
- `GET /api/v2/agent/llmlog?dialog=` — журнал запросов/ответов;
- `GET /api/v2/agent/actionlog?dialog=` — лог действий;
- `POST /api/v2/agent/analyze` — анализ диалога или всех диалогов скрипта выбранной
  моделью анализа; вход включает транскрипт, память, журналы LLM и действий.

Скрипт выполняется на фронтенде последовательными вызовами `/api/v2/agent/chat`
(отдельного `/api/v2/agent/script` нет): каждый диалог получает свежую сессию,
а результаты собираются в сравнительную таблицу.

Логирование действий пользователя: фиксация на сервере внутри самих операций
(память/настройки/скрипт/анализ логируются автоматически, «отправил сообщение» —
в начале хода), плюс `POST /api/v2/agent/action` для чисто UI-действий. Пауза,
продолжение и прерывание также обязательно попадают в журнал.

## 6. Анализ диалога

Кнопка «Анализ диалога» на панели B. Используется **модель анализа**, выбранная
отдельно от основной модели на панели C; её идентификатор сохраняется в журнале
вместе с запросом. Входной промпт для модели анализа включает ВСЁ:

1. транскрипт диалога;
2. снимки трёх слоёв памяти (текущие) + историю их изменений из логов;
3. журнал LLM-запросов (в т.ч. разбивка токенов по слоям, срабатывания сжатия ST);
4. **лог действий пользователя** (редактирования/очистки памяти и конфига агента,
   смена настроек, паузы/прерывания, загрузка скрипта, запуски анализа).

Модель отвечает структурой: качество ответов, корректность работы памяти
(что попало/не попало в промпт, лишнее), расход токенов по слоям, рекомендации
по настройкам (режим сжатия ST, N). Результат — в панели A под диалогом +
экспорт в .md (как в v1).

## 7. Скрипт диалога

Формат v1 (`{"dialogs": [{"name", "settings", "messages"}]}`) + опциональные
v2-поля (`stMessages`, режим сжатия ST, …). Прогон: свежая сессия на диалог,
очистка ST/WT; глобальный конфиг агента LT не изменяется и применяется ко всем
диалогам. Фактически отправленный LT сохраняется в каждом `request_json`, поэтому
результаты воспроизводимо проверяются даже после последующей правки конфига.
Агрегированные метрики + средние токены по слоям выводятся в сравнительную таблицу.
«Анализ скрипта» — тот же механизм анализа, но по всем диалогам скрипта сразу.

## 8. Этапы реализации

1. **Каркас**: `web/v2/agent.html` (4 панели, настройки над чатом), `AgentV2Session`
   без памяти (чистый чат с инструментами), SSE, `v2_dialogs`/`v2_entries`,
   восстановление. Сразу добавляются выбор основной модели и модели анализа,
   блокировка настроек во время выполнения, пауза/продолжение и прерывание.
2. **Память**: `MemoryStore`, таблицы, `MemoryAssembler` (полный LT/WT + все режимы
   сжатия ST), обновление working по рабочим правилам из раздела 3.7.
3. **Инспектор**: панель D (системный промпт, слои, токены), `TokenEstimator`,
   журнал LLM as is (сворачиваемый список, просмотр request/reasoning/response).
   SSE `reasoning` отображается в чате отдельным блоком «🧠 Размышления», открытым во время
   генерации и автоматически сворачиваемым после завершения или остановки хода. Reasoning
   остаётся самостоятельным блоком перед ответом и в этом же виде восстанавливается. Каждый вызов
   также показан в чате бледным сворачиваемым блоком с понятным названием; полные данные
   загружаются по `logId` из журнала, а ссылка `llmref` сохраняет порядок в транскрипте.
   Обычные вызовы не имеют второго уровня; у планирования первый уровень содержит пункты плана,
   второй — технические подробности.
4. **Редактирование памяти и конфига агента** + очистка слоёв, лог действий пользователя.
5. **Скрипты и анализ**: загрузка/прогон, сравнительная таблица с токенами по слоям,
   «Анализ диалога»/«Анализ скрипта» с полным пакетом данных и явно выбранной моделью.
6. **Проверка и спецификация**: компиляция, ручной сценарий (конфиг LT → задача WT →
   сжатие ST → токены → правка → пауза/продолжение → прерывание → очистка → скрипт →
   анализ), обновление `readme_0.md` (раздел v2: страница, API, таблицы, правила памяти).

## 9. Ручные тесты приёмки

- Панель настроек расположена **над чатом** и содержит независимые списки основной
  модели и модели анализа; основной ответ и анализ выполняются именно выбранными моделями.
- Во время хода, скрипта и анализа все настройки заблокированы; после `done`, `error`
  и прерывания снова доступны. Во время паузы разблокировки не происходит.
- «Пауза» останавливает агента перед следующим шагом, «Продолжить» возобновляет ход
  без потери контекста; кнопка прерывания доступна и на паузе, и во время LLM-вызова.
  Во время скрипта пауза также не даёт начать следующее сообщение после завершения текущего,
  независимо от наличия шагов с инструментами; прерывание снимает ожидание.
- «Прервать» завершает текущий ход с `aborted=true`, разблокирует UI и останавливает
  дальнейшее выполнение скрипта; pause/resume/abort видны в логе действий.
- Под каждым ответом ассистента выводятся входные, выходные и общие токены всего хода, числа
  вызовов LLM и инструментов, длительность и признак прерывания. Нижняя панель показывает суммы
  этих метрик по всем ходам видимого чата. API истории возвращает `turnstats`, по которым обе
  статистики восстанавливаются без повторного учёта `lastTurn`; новая задача сбрасывает суммы.
- Конфиг агента из **long-term** хранится как валидный JSON с типизированными правилами,
  попадает целиком в каждый основной запрос и действует в новом диалоге; факты
  пользователя и задачи туда автоматически не записываются.
- «Новая задача» создаёт диалог с пустыми ST/WT и прежним LT; «Сбросить всё» после
  подтверждения очищает все слои, но сохраняет транскрипты и журналы.
- Sticky-факты относятся только к своему диалогу и не появляются в новом диалоге.
- WT содержит формулировку задачи, критерии приёмки и ограничения; все они видны
  в следующем запросе as is и доступны для ручной правки.
- LT и WT никогда не урезаются: при переполнении окна сжимается только ST; если этого
  недостаточно, запрос останавливается с ошибкой вместо обрезки конфига или задачи.
- Смена режима сжатия ST (none/lastN/sliding/sticky/summary) видна в журнале LLM as is.
- Чипы токенов слоёв меняются при очистке/редактировании слоя; оценка ≈ факт usage.
- Журнал LLM содержит каждый вызов as is, включая служебные извлечения фактов и summary.
- Очистка слоя немедленно отражается в следующем запросе (видно в журнале).
- Лог действий содержит все пользовательские операции и попадает в анализ.
- Скрипт из 4 диалогов прогоняется, таблица показывает токены по слоям; анализ диалога
  и скрипта использует модель, выбранную в настройках, а не только `llm.analysis.model`.
